# Observability

## Overview

After deploying the application to Kubernetes, the next step was implementing an observability platform. Running workloads successfully is only part of operating a production environment. It is equally important to understand the health of the infrastructure, monitor application behavior, and quickly identify the root cause of failures.

Observability was introduced to provide centralized visibility into both system metrics and application logs. Instead of manually inspecting individual Pods, all operational data is collected and visualized from a single platform.

Although monitoring and logging are closely related, they serve different purposes:

- **Monitoring** answers **what is happening** by collecting time-series metrics such as CPU usage, memory consumption, request rates, and latency.
- **Logging** answers **why it happened** by recording detailed events generated by applications and Kubernetes workloads.

Combining both capabilities significantly reduces troubleshooting time and provides a much clearer understanding of the overall platform state.

The monitoring platform was deployed in a dedicated Kubernetes namespace named `monitoring`.

Separating observability components from application workloads improves organization, simplifies resource management, and isolates monitoring services from business applications.

This separation also makes it easier to apply namespace-specific policies, manage permissions, perform upgrades, and monitor multiple applications from a centralized observability stack.

## Monitoring Stack

To simplify deployment and maintenance, the monitoring platform was installed using the **kube-prometheus-stack** Helm chart instead of deploying each monitoring component individually.

This approach provides a production-ready monitoring stack while ensuring all components are already configured to work together.

The deployed monitoring stack includes:

- Prometheus
- Grafana
- Alertmanager
- kube-state-metrics
- node-exporter
- Prometheus Operator

One of the biggest advantages of this stack is the **Prometheus Operator**.

Instead of manually editing Prometheus configuration files every time a new application needs monitoring, the Operator continuously watches Kubernetes resources and automatically updates the Prometheus configuration. This Kubernetes-native approach greatly simplifies service discovery and reduces operational overhead.

## Prometheus

Prometheus is responsible for collecting, storing, and querying application and infrastructure metrics.

Unlike push-based monitoring systems, Prometheus follows a **pull model**. At regular intervals, it requests metrics from configured targets through HTTP endpoints.

This approach offers several advantages:

- Automatic health verification during scraping
- Native Kubernetes service discovery
- Easy addition of new monitored services
- Reliable time-series metric storage

Within this implementation, Prometheus collects metrics from multiple sources:

- Kubernetes cluster components
- Node-level metrics exposed by node-exporter
- Kubernetes object metrics exposed by kube-state-metrics
- Spring Boot application metrics

The backend exposes application metrics through **Spring Boot Actuator** using **Micrometer**. Micrometer automatically instruments the application and publishes metrics through the `/actuator/prometheus` endpoint.

These metrics include JVM statistics, HTTP request metrics, memory usage, CPU utilization, and many other runtime indicators without requiring custom instrumentation.

## ServiceMonitor

Rather than maintaining static Prometheus scrape configurations, the application is monitored using a Kubernetes **ServiceMonitor** resource.

This resource is managed by the Prometheus Operator and enables automatic service discovery inside the cluster.

The backend Service is labeled with:

```yaml
monitoring: enabled
```

The ServiceMonitor watches for Services containing this label and automatically registers them as Prometheus scrape targets.

The backend exposes its monitoring endpoint through a dedicated management port.

Prometheus scrapes metrics from:

- Management port
- Endpoint: `/actuator/prometheus`
- Scrape interval: **15 seconds**

Using ServiceMonitor keeps the monitoring configuration declarative and eliminates manual updates whenever monitored services change.

## Grafana

While Prometheus stores raw metrics, Grafana provides the visualization layer used to analyze them.

Grafana connects directly to Prometheus and transforms collected metrics into dashboards that provide real-time operational insights.

A dedicated dashboard was created for monitoring the backend application.

The implemented dashboard includes:

- **Backend Runtime**
- **JVM CPU Usage**
- **Heap Memory Usage**
- **HTTP Requests/sec**
- **HTTP 5xx Errors/sec**
- **HTTP P95 Latency**

These panels provide immediate visibility into application health and runtime behavior.

For example:

- Runtime confirms application availability.
- JVM CPU Usage helps identify excessive CPU consumption.
- Heap Memory Usage monitors Java memory utilization.
- HTTP Requests/sec displays incoming traffic.
- HTTP 5xx Errors/sec highlights server-side failures.
- HTTP P95 Latency helps identify slow request processing.

Together, these metrics provide a concise overview of application performance.

## Centralized Logging

Metrics alone cannot explain why an application behaves unexpectedly. For that reason, centralized logging was added to the observability stack.

Instead of inspecting logs directly from Kubernetes Pods, all application logs are collected into a single centralized storage system.

This implementation uses:

- Promtail
- Loki
- Grafana

Promtail continuously watches Kubernetes container logs and forwards them to Loki.

Loki stores logs together with their Kubernetes labels, making them searchable without requiring complex indexing.

Loki was selected instead of Elasticsearch because it is significantly lighter for Kubernetes environments and integrates seamlessly with Grafana. Since Loki indexes labels rather than the complete log contents, it requires fewer resources while still providing efficient log exploration.

To provide persistent log storage, Loki is configured to use **MinIO** as its object storage backend.

## Log Dashboard

A dedicated Grafana dashboard was created to explore application logs collected by Loki.

The dashboard provides filtering capabilities for:

- Container
- Service
- Instance
- Custom search expressions

Several panels were implemented to simplify log analysis:

- **All Requests**
- **Frontend Access Logs**
- **Error Logs**
- **Exception Logs**
- **All Logs Count**
- **All Service Logs per Instance**
- **Historical Log Count per Instance**

These panels make it possible to inspect requests, monitor service activity, identify failed operations, and quickly locate runtime exceptions without directly accessing Kubernetes Pods.

Because Grafana queries Loki in real time, new log entries become immediately available during troubleshooting.

## Metrics and Logs Correlation

Observability becomes significantly more valuable when metrics and logs are analyzed together.

Metrics indicate that an issue exists, while logs explain the reason behind it.

The implemented workflow follows a simple troubleshooting process:

```
Metric anomaly detected
        │
        ▼
Identify the affected service
        │
        ▼
Open related logs in Grafana
        │
        ▼
Inspect requests, errors or exceptions
        │
        ▼
Identify the root cause
```

Using Grafana as a unified interface allows operators to move naturally between performance metrics and application logs, reducing investigation time and improving incident response.

## Benefits

The implemented observability platform provides several operational advantages:

- Centralized monitoring for infrastructure and applications
- Centralized log aggregation
- Real-time visibility into application health
- Faster incident investigation
- Easier production debugging
- Reduced troubleshooting time
- Better operational awareness
- Simplified monitoring of Kubernetes workloads
- Unified interface for metrics and logs

Together, these capabilities improve day-to-day platform operations while making production issues easier to detect and resolve.

## Summary

The observability implementation includes:

- Deployment of the **kube-prometheus-stack** using Helm
- Automatic metrics collection with **Prometheus**
- Kubernetes-native service discovery using **ServiceMonitor**
- Backend metrics exposed through **Spring Boot Actuator** and **Micrometer**
- Custom Grafana dashboard for JVM and HTTP metrics
- Centralized log collection using **Promtail**
- Log storage using **Loki**
- Persistent Loki storage backed by **MinIO**
- Custom Grafana logging dashboard
- Unified analysis of metrics and logs through Grafana

This implementation provides a production-oriented observability platform capable of monitoring application health, collecting runtime metrics, centralizing logs, and accelerating operational troubleshooting within the Kubernetes environment.
